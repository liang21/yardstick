## 核心判断

从资深测试转 AI 评测，**核心资产不是编程，而是"怎么定义质量、怎么设计覆盖、怎么发现边界 case"这套方法论**。这套东西在 AI 评测里价值更高，因为 AI 系统没有确定性断言可用。

需要补的是三样：概率思维、基础统计、大模型工程常识。

### 思维方式的三个转变

| 传统测试 | AI 评测 |
|---|---|
| `assert result == expected` | 分布上的质量度量，同一输入多次结果不同是正常的 |
| 用例是手段，产品是目标 | **评测集本身就是核心资产**，要版本化、分层、持续回流 |
| 通过/失败 | 带噪声的分数，要看方差、置信区间、显著性 |

额外一条：**数据污染**。训练集里见过的题，评出来的分数没有意义。

## 贯穿项目

不要"先学完知识再动手"——AI 评测的坑几乎全在实操里。整条路径围绕一个项目展开。

**选题建议**：用你现在测的业务域。比如产品帮助文档 + API 文档 + 历史工单。

目标做成两个东西：

1. **文档问答 RAG** —— 阶段 1、2 评它
2. **工单处理 Agent** —— 加上工具调用，比如「查订单状态 → 判断是否可退 → 生成回复」，阶段 3 评它

用熟悉的业务，面试时你能讲清楚"这个场景什么叫答得好"，而不是背指标定义。

## 阶段 0：打地基（2 周）

### 学

- Python 的 requests / 异步并发（评测要批量跑）
- pandas 基础：groupby、透视、合并
- 模型 API 参数含义：temperature、top_p、seed、max_tokens

### 做

写一个脚本：读入 CSV 里的 100 个问题 → 并发调模型 → 结果存成结构化文件。同一个问题跑 5 次，用 pandas 统计答案差异。

### 验收

能说清楚 **temperature=0 为什么也不能保证完全复现**。

---

## 阶段 1：第一套 RAG 评测（3 周）

### 学

RAG 完整链路：文档切块 → embedding → 向量检索 → 重排 → 拼 prompt → 生成。

重点认知：**每一环都会独立出错，评测要能定位到环**。

### 做

| 周 | 任务 |
|---|---|
| 第 1 周 | 用 LlamaIndex 或 LangChain 搭起最简 RAG，跑通 |
| 第 2 周 | 手写 50 条问题，标出参考答案和应该命中的文档片段。**手工做，不要用模型生成**，你需要体感 |
| 第 3 周 | 装 Ragas 跑一遍，理解四个核心指标各自在测什么 |

### RAG 四个核心指标

| 指标 | 在测什么 | 低了找谁 |
|---|---|---|
| 忠实度 faithfulness | 答案有没有超出检索内容瞎编 | 生成环节 / prompt |
| 答案相关性 | 答案是否回应了问题 | 生成环节 |
| 上下文精确率 | 检索回来的内容有多少是有用的 | 检索 / 重排 |
| 上下文召回率 | 该检索到的内容有没有漏 | 切块 / embedding / 检索 |

### 验收

能画出一张表，说明"检索召回率低"和"忠实度低"分别该找哪个环节的同学修。

> 这是你作为测试的核心价值。**别只交一个总分。**

## 阶段 2：评测集工程 + judge 校准（5 周）

> **整条路径的分水岭，慢一点没关系。**

### 学

- **评测集设计**：分层（高频 / 长尾 / 边界 / 对抗）、难度分级、每条 case 的元数据（场景、期望行为、来源）
- **标注规范怎么写**：rubric 要能让两个人打出同样的分
- **LLM-as-judge 的系统性偏差**：位置偏见、长度偏见、自我偏好、评分集中在中间档
- **一致性统计**：Cohen's Kappa、Spearman 相关系数

### 做

**第 1–2 周：评测集扩到 200 条**

分层要有意识，不只是"能答对的常见问题"，必须包含：

- 文档里根本没有答案的问题（考它会不会编）
- 问法刁钻但意图明确的问题
- 需要跨多个文档的多跳问题
- 前提有误的问题（"你们的退款周期为什么是 30 天？"但实际是 7 天）

**第 3 周：写 rubric + 人工标注**

- 写一份 3–5 档的打分 rubric
- 自己先人工标一遍全部 200 条
- 找一个同事标其中 50 条，算你俩的 Kappa
- **低于 0.6 就改 rubric 重来** —— 说明标准本身没写清楚

**第 4–5 周：搭 judge 并校准**

- 用 DeepEval 或自己写 prompt 搭 judge
- 让它标同样 200 条，算 judge 与人工的一致性
- 迭代 judge 的 prompt：加 few-shot、改成分项打分、改成两两对比（pairwise）

### 验收

拿出一张 **「judge 版本 vs 人工一致性」的迭代曲线**。

> 这一个产出物，面试里比什么都管用——绝大多数人只会用 judge，不会验证 judge。

## 阶段 3：Agent 与多轮对话评测（4 周）

### 学

- **Function Calling 的失败模式**：该调工具时不调、调错工具、参数填错、结果理解错、死循环
- **轨迹评测 vs 结果评测**：任务最终完成了，但中间多调了 6 次工具，这算通过吗
- **多轮对话的独特问题**：上下文漂移、前后矛盾、人设崩塌、指代消解失败

### 做

| 周 | 任务 |
|---|---|
| 第 1 周 | 给 RAG 加上 2–3 个工具（查订单、查政策、建工单），跑起来 |
| 第 2 周 | 设计 30 个多步任务，每个写清楚**期望轨迹**和**可接受的替代轨迹** |
| 第 3 周 | 实现轨迹级指标 |
| 第 4 周 | 多轮对话：用一个模型扮演用户，和系统对打 10 轮，评一致性和上下文保持 |

### Agent 指标集

- 工具选择准确率
- 参数填充正确率
- 任务完成率
- 平均步数
- 平均 token 成本
- 异常恢复率（工具报错后能否正确处理）

### 验收

能回答"这个 Agent 到底哪里不行"——是**规划能力差**，还是**工具描述写得烂**。

## 阶段 4：评测流水线与回归（3 周）

> 这阶段你的老本行直接派上用场。

### 学

- **四元版本追溯**：prompt 版本、模型版本、数据集版本、代码版本，四者要能对应
- 评测结果的统计显著性

### 做

- 接入 **Langfuse** 或 **Arize Phoenix** 做 tracing，能从一个低分 case 点进去看完整调用链
- 把评测封装成 **pytest**，写进 CI：
  - 每次 prompt 改动 → 自动跑核心子集（30 条冒烟）
  - 每晚 → 跑全量
- 设卡点：忠实度低于阈值就 fail
- 做一次**真实的 A/B**：换 embedding 模型或改切块大小，跑 5 轮，算均值和置信区间

### 验收

评测报告的结论写成：

> B 方案忠实度提升 4.2%，95% 置信区间 [1.1%, 7.3%]，差异显著。

而不是"B 比 A 高了 4 个点"。

## 阶段 5：线上评测与红队（3 周）

### 学

- 线上 / 线下评测的差异
- 采样策略与数据回流
- 用户反馈信号（点踩、重问、放弃）怎么变成评测集
- OWASP Top 10 for LLM Applications
- 越狱与 prompt 注入的常见手法
- 国内《生成式人工智能服务管理暂行办法》的备案与安全评估要求

### 做

**线上质量监控方案**，需要回答：采样多少、用哪个 judge、异常怎么告警、bad case 怎么回流。

**红队一轮**，用 promptfoo 或 DeepTeam，覆盖：

- prompt 注入
- 越狱
- 越权调用工具
- 敏感信息泄漏

### 验收

画得出完整闭环图：

```
线上采样 → 自动打分 → 人工复核 → 回流评测集 → 回归验证 → 线上采样
```

## 常见误区

| 误区 | 问题所在 |
|---|---|
| **跳过阶段 2 直接用现成指标跑分** | 学到的是调 API，不是评测。这是最容易翻车的地方 |
| 只学工具不学方法论 | 工具半年换一轮，方法论不会 |
| 迷信公开 benchmark 分数 | MMLU 这类榜单和你的业务场景几乎没关系 |
| 不做 judge 校验就上自动评测 | 等于用一把没校准的尺子量东西 |
| 把单次运行结果当结论 | 忽略了采样噪声，2% 的波动会被当成"优化生效了" |
| 想把传统测试经验全部扔掉 | 恰恰相反，风险识别、场景拆解、边界思维是你最值钱的部分 |
